## P0　正确性与稳定性

### [ ] 1. 修复 Prisma 生产环境单例失效

- **位置**：[server/utils/prisma.ts](../server/utils/prisma.ts)
- **现状**：只有 `process.env.NODE_ENV !== 'production'` 时才把实例写入 `globalThis` 缓存；PM2 设置了 `NODE_ENV=production`，因此生产环境每次调用 `usePrisma()` 都会新建 `PrismaClient` 和 PG 连接池。
- **影响**：单次请求可能创建多个客户端，例如 [overview.get.ts](../server/api/admin/analytics/overview.get.ts) 一次调用 6 次 `usePrisma()`；流量上来后可能出现 PostgreSQL `too many clients`、连接抖动和内存上涨。
- **方案**：所有环境都复用同一个全局实例：

  ```ts
  export function usePrisma() {
    if (globalForPrisma.prisma) return globalForPrisma.prisma

    const connectionString = process.env.DATABASE_URL
    if (!connectionString) {
      throw createError({ statusCode: 503, statusMessage: 'Database is not configured' })
    }

    const adapter = new PrismaPg({ connectionString })
    globalForPrisma.prisma = new PrismaClient({ adapter })
    return globalForPrisma.prisma
  }
  ```

- **附带优化**：handler 内使用 `const prisma = usePrisma()` 复用局部变量，减少重复调用。
- **验收**：生产模式多次调用返回同一实例；仪表盘等接口不再创建多客户端；`pnpm typecheck` 和 `pnpm build` 通过。

### [ ] 2. 部署链路增加质量门禁

- **位置**：[.github/workflows/deploy.yml](../.github/workflows/deploy.yml)
- **现状**：`push main` 后直接 rsync、安装依赖、迁移、构建、重载；没有 `pnpm typecheck`、lint 或测试。Nuxt build 默认不做类型检查，类型错误可能直接进入生产。
- **方案**：增加 GitHub-hosted 的 `verify` job，让 deploy 依赖它：

  ```yaml
  - run: pnpm install --frozen-lockfile
  - run: pnpm exec prisma generate
  - run: pnpm typecheck
  # 后续有测试后：pnpm test
  ```

- **验收**：verify 失败时 deploy 不执行；成功时保持现有部署流程不变。

## P1　稳定性与工程化

### [ ] 3. 证书续期监控与替换自动化

- **位置**：Nginx / 腾讯云 SSL 控制台
- **现状**：线上证书有效期至 **2026-12-18 08:59:59 UTC**（2026-10-17 核实），腾讯云自动续费不会自动替换 CVM 上的证书文件。
- **方案**：
  - 增加到期前 30 天提醒或定时检查（GitHub Actions schedule / 服务器 cron）。
  - 将“下载 → 核对 → 替换 `.crt` / `.key` → `nginx -t` → reload”写成脚本。
  - 评估迁移到 Certbot 自动续签。
- **验收**：到期前完成替换，HTTPS 访问正常，证书链和 SAN 覆盖根域名与 `www`。

### [ ] 4. 数据库备份自动化与恢复演练

- **位置**：生产服务器 / 部署文档第 21 节
- **现状**：目前只有手工 `pg_dump` 流程。
- **方案**：
  - 使用 systemd timer 或 cron 定时执行 `pg_dump -Fc`。
  - 备份文件加密后同步到异地存储，保留周期明确。
  - 定期在空数据库执行 `pg_restore` 恢复演练。
- **验收**：任意一次备份可在测试库恢复，记录恢复耗时和校验结果。

### [ ] 5. 引入 lint / format / test 工具链

- **位置**：[package.json](../package.json)、CI
- **现状**：没有 `lint`、`test` 脚本，也没有 ESLint / Prettier / Vitest；本次手工展开了压缩文件，但缺少工具防止回归。
- **方案**：
  - 引入 `@nuxt/eslint` + Prettier，增加 `lint`、`format:check` 脚本。
  - 引入 Vitest，优先覆盖 `readingMinutes`、Markdown 清洗、Zod Schema、认证工具。
  - CI 中执行 `lint` + `typecheck` + `test` 后再允许部署。
- **验收**：本地和 CI 均可运行；格式错误和测试失败能阻断合并/部署。

### [ ] 6. SEO 收尾

- **位置**：页面 SEO 配置、[sitemap.xml.get.ts](../server/routes/sitemap.xml.get.ts)、[robots.txt.get.ts](../server/routes/robots.txt.get.ts)
- **待办**：
  - 补齐 **Canonical**、**Twitter Card** 和文章 JSON-LD 结构化数据。
  - Sitemap 静态页面的 `lastmod` 目前每次请求取 `new Date()`，会持续变化；改为固定构建时间或省略。
  - `robots.txt` 的 `base` 未去除末尾 `/`，当 `NUXT_PUBLIC_SITE_URL` 带斜杠时会生成双斜杠。
- **验收**：关键页面有唯一 canonical；社交分享卡片正常；sitemap/robots 输出稳定。

### [ ] 7. 配置读取与 Session 卫生

- **位置**：[server/utils/settings.ts](../server/utils/settings.ts)、Session 相关逻辑
- **待办**：
  - `getSettings()` 目前直接 `as SiteSettingValue`，建议改用 `settingsSchema.safeParse` 校验，失败回退默认值并记录日志。
  - `Session.lastSeenAt` 字段存在但从未更新：要么按小时更新，要么后续迁移删除。
  - 过期 Session 目前只在被访问时清理，建议增加定期清理任务。
- **验收**：手工写入异常设置时页面仍可回退；Session 表不会长期积累过期记录。

## P2　体验与性能

  - 顶部阅读进度条。
  - TOC 当前标题高亮。
- **验收**：文章间导航可用；长文阅读进度准确；移动端不遮挡正文。

### [ ] 10. 自定义错误页

- **现状**：没有 `app/error.vue`，404/500 使用 Nuxt 默认页面。
- **方案**：增加与前台风格一致的自定义错误页，提供返回首页和文章列表入口。
- **验收**：非法文章 ID、未知路由、服务端异常均显示统一错误页。

### [ ] 11. 图片加载细节

- **位置**：首页头像、文章封面、项目卡片等
- **待办**：
  - 封面和头像补 `loading="lazy"`、`referrerpolicy="no-referrer"`。
  - 视情况补充宽高或 `aspect-ratio`，减少 CLS。
- **验收**：外部图床拒绝 Referer 时图片仍可显示；首屏布局不抖动。

### [ ] 12. 类型安全与共享类型

- **现状**：页面中存在较多 `useFetch<any>`，前后端类型未复用。
- **方案**：把 `PublicPost`、`SiteSettingValue`、`Project` 等类型整理到 `shared/types` 或从 Zod Schema 推导。
- **验收**：主要页面和 API 不再依赖 `any`；类型变更时前端能及时报错。

### [ ] 13. 构建体积分析与优化

- **现状**：后台部分依赖 chunk 较大（如 `Select`、`Button`），`entry` CSS 约 199 KB。
- **方案**：使用 `nuxi analyze` 查看 bundle，确认是否有后台专用依赖被前台引入；按需懒加载后台组件。
- **验收**：前台首屏 JS/CSS 体积有明确基线，优化后有可对比数据。

### [ ] 14. 运行时版本约束

- **现状**：本地 Node 24，生产 Node 22，`package.json` 没有 `engines`。
- **方案**：声明 `"engines": { "node": ">=22" }`，并统一 CI、生产和本地版本。
- **验收**：安装依赖时能提示不兼容版本；CI 与生产使用同一大版本。
